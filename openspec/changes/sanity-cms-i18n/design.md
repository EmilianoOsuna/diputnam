## Context

Ver `proposal.md`. Estado relevante: Astro 7 SSG sin adapter, `build.inlineStylesheets: 'always'`, publicado con `wrangler deploy` como assets estáticos (sin CI en el repo; el host cambiará a Vercel). Seis páginas `.astro` monolíticas (`src/pages/*.astro`) que importan datos de `src/data/*.ts` y mezclan literales de UI y contenido; `SiteHeader` lleva un `ES` estático y los links en duro. Imágenes: mocks remotos pasados por `remoteImage()`/`remoteSrcset()` (`w`, `q`, `sat` en la URL) y tres JPG de contenido en `src/assets/`. Títulos con saltos editoriales de dos clases: `\n` + `white-space: pre-line` (home, salto siempre) y `<br class="cut">` (interiores, salto solo ≥ 768 px). `splitLines` cierra renglón en `<br>` y `\n`. Tests Playwright (`tests/*.mjs`) iteran seis rutas contra `BASE_URL`; `tests/check-dist.mjs` corre en `postbuild`.

## Goals / Non-Goals

**Goals:** el sitio sigue siendo 100 % estático y su build reproducible desde cualquier host con dos variables de entorno; una sola plantilla por página para ambos idiomas; el admin edita todo el contenido, imágenes y PDFs desde un Studio; el pipeline de imágenes conserva srcset/sat/hotspot sin filtros CSS; ninguna decisión ata el código a Cloudflare o Vercel.

**Non-Goals:** preview de borradores en el sitio (Visual Editing / Presentation); SSR o ISR; comentarios, búsqueda o paginación de noticias; traducir el Studio; cambiar la dirección de arte de ninguna página; formulario de contacto conectado a Sanity.

## Decisions

- **D1. Rutas: plantillas en `src/views/`, rutas delgadas por idioma.** Cada página se mueve a `src/views/<pagina>.astro` (documento completo, recibe `lang`) y `src/pages/` queda con archivos de una línea: `src/pages/contacto.astro` → `<Contacto lang="es" />`, `src/pages/en/contact.astro` → `<Contacto lang="en" />`. `astro.config.mjs` declara `i18n: { defaultLocale: 'es', locales: ['es','en'], routing: { prefixDefaultLocale: false } }` para `Astro.currentLocale` y los helpers de URL. Los slugs por idioma viven en `src/i18n/routes.ts` (`{ contacto: { es: '/contacto/', en: '/en/contact/' } }`) y alimentan header, `hreflang` y selector. *Alternativa*: `src/pages/[...locale]/x.astro` con `getStaticPaths` — descartado porque los slugs en inglés difieren (`news`, `join`, `contact`) y obliga a rutas dinámicas por todo. *Alternativa*: `astro-i18next`/`paraglide` — descartadas, Astro nativo basta.
- **D2. Diccionario tipado con verificación en build.** `src/i18n/es.ts` es la fuente de claves (`as const`); `src/i18n/en.ts` se declara con el tipo derivado (`satisfies Dictionary`) para el error en editor y `src/i18n/index.ts` compara los conjuntos de claves al cargar y lanza si difieren (falla `astro build` aunque no corra `astro check`). `t(lang)` devuelve el diccionario; en las vistas `const ui = t(lang)`. Nada de interpolación compleja: los pocos casos con números (`"{n} notas publicadas"`) se resuelven con funciones en el propio diccionario.
- **D3. Studio en `studio/` con `package.json` propio, no workspace.** Las dependencias del Studio (React, `sanity`) no deben instalarse en el build del sitio; `npm ci` en la raíz sigue igual de ligero. `sanity deploy` publica en `putnam.sanity.studio`. Un solo dataset `production`; sin dataset de staging en free tier (los borradores ya cumplen esa función).
- **D4. Modelo de contenido.** Tipos objeto `localeString`/`localeText` (`{ es: required, en }`) y `localeImage` (`image` con `hotspot: true` + `alt: localeString` + `decorative: boolean`). Singletons (un documento por tipo, ocultos de "crear nuevo" en la estructura del Studio): `home` (escenas), `eredita` (hero, intro, facts, galería, tipologías, intro de documentos), `putnam`, `unete`, `contacto` (hero, canales, motivos, ubicación, formulario y CTA: el copy que antes vivía en línea en la plantilla), `noticias` (hero, índice y CTA del listado), `siteSettings` (datos de contacto, horarios). Documentos: `nota` (con `@sanity/document-internationalization`, campo `language` + `translation.metadata`), `documentoLegal`. Los datos de contacto salen de `src/data/home.ts` a `siteSettings` porque los usan header, footer y CTAs de todas las páginas. *Alternativa*: `nota` con campos `{es,en}` — descartado por la decisión de permitir notas en un solo idioma.
- **D5. Saltos de línea editoriales.** Los títulos son campos `text` (multilínea). Un componente `<Lines text mode>` parte por `\n`: `mode="hard"` renderiza `<br>` (escenas del home, sustituye `white-space: pre-line`) y `mode="cut"` renderiza `<br class="cut">` (h1/h2 interiores, salto solo en desktop, comportamiento actual). `splitLines` no cambia. El Studio muestra una descripción en el campo: "Intro = salto de renglón".
- **D6. Cuerpo de nota en Portable Text** renderizado con `astro-portabletext`; bloques permitidos: párrafo, h2/h3, listas, enlace, imagen (`localeImage`). Sin embeds ni tablas.
- **D7. Documentos legales: archivo opcional, versión obligatoria con archivo, y reemplazo con cambio de versión verificado.** Schema `documentoLegal { title, description: locale, order, file (accept application/pdf), version: string, validFrom: date }` con `Rule.custom`: si hay `file`, `version` y `validFrom` son obligatorios; además la validación obtiene el documento publicado vía `context.getClient()` y rechaza publicar si `file.asset._ref` cambió y `version` no. El historial de Sanity conserva las revisiones anteriores; la tarjeta muestra `v · fecha` y tamaño (`file.asset->size`). La URL del CDN es única por asset, así que el enlace de cada versión es estable.
- **D8. Imágenes: URL de Sanity + `object-position` para el hotspot.** Las consultas proyectan `{ url: asset->url, crop, hotspot, alt, decorative, width, height }`. `src/lib/images.ts` añade en `remoteImage` la rama `cdn.sanity.io`: `w`, `q`, `auto=format`, `sat` (Sanity lo soporta) y `rect` cuando hay `crop`; el srcset se genera igual que hoy. El hotspot se aplica como `style="object-position: x% y%"` sobre el `<img>` con `object-fit: cover`, así el recorte por aspecto lo sigue haciendo CSS y no hace falta un `h` por candidato. Los mocks de Unsplash/Contentful y el código de `images.ctfassets.net` se eliminan; `check-dist.mjs` añade el guard de hosts mock. *Alternativa*: `@sanity/image-url` con `fit('crop').focalPoint()` — genera `h` fijo por variante y rompe la paridad de srcset; descartado.
- **D9. Cliente y consultas.** `src/lib/sanity.ts` crea `@sanity/client` con `useCdn: true`, `perspective: 'published'`, `apiVersion: '2026-09-01'`, y lanza un error nombrando la variable ausente si faltan `SANITY_PROJECT_ID`/`SANITY_DATASET` (vía `import.meta.env`, no `PUBLIC_`). `src/lib/content.ts` expone `getHome(lang)`, `getEredita(lang)`, `getNotas(lang)`, `getNota(lang, slug)`, `getLegalDocs(lang)`, `getSettings(lang)` con GROQ que resuelve el fallback en la consulta: `"title": coalesce(title[$lang], title.es)`. Las vistas reciben objetos ya localizados, sin lógica de idioma en el markup. *Alternativa*: `@sanity/astro` (integración + `sanity:client`) — descartada para no depender de la integración ni exponer el Studio embebido.
- **D10. Regeneración: webhook → una URL.** El webhook GROQ de Sanity (`_type in [...]`, create/update/delete) llama a una URL con secreto. Con Vercel esa URL es su deploy hook nativo. Mientras el host sea Cloudflare Workers (sin deploy hook nativo para `wrangler deploy`), la URL es `repository_dispatch` de GitHub y un workflow `.github/workflows/deploy.yml` hace `npm ci && npm run build && wrangler deploy`; el mismo workflow corre en push a `main`. Cambiar de host = cambiar la URL del webhook y retirar el workflow. Ningún código del sitio conoce el host.
- **D11. Seed.** `studio/scripts/seed.ts` lee `src/data/*.ts` de la última revisión que los contiene, sube cada imagen mock como asset (`client.assets.upload`) y crea los documentos con `createOrReplace` e ids deterministas (`home`, `eredita`, `nota.<slug>`, `doc.<slug>`). El inglés del contenido editorial se redacta en `studio/scripts/seed.en.ts` para revisión del usuario antes de ejecutar. Se ejecuta una vez contra `production`; queda en el repo como referencia y para recrear un dataset.
- **D12. Verificación.** `routes` de `mobile-audit`, `mobile-perf` y `home-sweep` pasan a doce (lista importada de `src/i18n/routes.ts` para no duplicar); `check-dist` verifica `/_image?`, hosts mock, `hreflang` recíproco y `lang` en cada HTML. Los tests corren contra `astro preview` de un build con credenciales; sin credenciales el build falla antes.

## Risks / Trade-offs

- [Cuota free tier: 100k requests/mes de API, 10 GB assets, 10 GB bandwidth] → el build hace ~8 consultas con `useCdn`; con Playwright y decenas de builds diarios sigue bajo 1 %. Los PDF se sirven desde el CDN y cuentan como bandwidth: aceptable para documentos de pocos MB.
- [Cada `Publish` dispara un build completo] → aceptable a esta escala; si el admin publica en ráfaga, el deploy hook agrupa (Vercel) o GitHub encola. No se implementa debounce.
- [Contenido en inglés incompleto al lanzar] → el fallback al español garantiza páginas completas; las notas sin traducción no aparecen en `/en/news/`. El listado en inglés puede quedar vacío el primer día: estado vacío diseñado en el spec.
- [Validación D7 depende de leer el documento publicado desde el Studio] → si la lectura falla, la validación deja publicar (no bloquea el trabajo) y se registra en consola; el historial de Sanity sigue siendo la red de seguridad.
- [`object-position` no recorta igual que `fit=crop` con `h`] → visualmente equivalente para `object-fit: cover`; se verifica con el audit de hotspot a 390 px.
- [Contenido editable rompe títulos: un título largo desborda a 320 px] → la comprobación existente de `title-line-reveal` en `mobile-audit` sigue vigente y el Studio limita la longitud de los títulos de escena (validación `max`).
- [Studio fuera del build del sitio → dos `npm install`] → aceptado; documentado en README con los comandos `npm run studio:dev`/`studio:deploy` desde la raíz.

## Migration Plan

1. i18n en código con datos locales (sin Sanity) y deploy: el sitio sale bilingüe con contenido en `src/data`. Punto de rollback natural.
2. Crear proyecto Sanity, Studio y schemas; ejecutar seed; desplegar Studio. El sitio aún no lee Sanity.
3. Cambiar las vistas a `src/lib/content.ts`, borrar `src/data` y mocks, configurar variables en el host, deploy. Rollback: revertir el commit de este paso; el contenido en Sanity permanece.
4. Configurar webhook y deploy hook (workflow de GitHub mientras el host sea Cloudflare). Al migrar a Vercel: variables de entorno, deploy hook, actualizar URL del webhook, retirar workflow.
